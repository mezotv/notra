02 / Follow a scan

From cron tick to final result.

The tests cover separate parts of this path. This diagram is the production flow, not a claim that one deployed end-to-end test traverses it all.

  1. 01

    Authorize

    Check the cron bearer secret. Reject missing or incorrect credentials before scanning.

  2. 02

    Find due projects

    Clean abandoned scans. Select enabled, due schedules, up to 25 per sweep.

  3. 03

    Claim & hand off

    Advance the next tick. Acquire the slot, create a pollable scan row, pass its token to the workflow.

  4. 04

    Run batches

    Process tasks and sequences. Pass each renewed token to the next batch and accumulate results.

  5. 05

    Finalize

    Persist the verdict and release the owned slot. Retry once if attempted work produced no checks.

Ownership token: the scan’s claimedAt timestamp. Database updates compare this token before clearing a slot, so an old worker cannot finish a newer worker’s run.
A ∥ B

Two triggers arrive together

Several sweeps or claim attempts target the same project. The assertions require a single winning claim and one workflow hand-off.

Expected: start the project once.
503 → release

The hand-off is rejected

An explicit internal-route rejection means nothing started. The pending scan is marked failed, its slot is released, and other projects continue.

Expected: no phantom running scan.
timeout → hold

The outcome is unknown

A timeout may happen after the workflow was accepted. Keep the claim and the running row until completion or stale recovery.

Expected: do not risk a second paid scan.
03 / Inside the new suite

Five areas. Concrete failure cases.

Expand each area to see the behavior being checked and the boundary between production code and test infrastructure.

Cron & persisted scan lifecycle

15 new
  • Due and migrated schedules run; disabled and future schedules stay untouched.
  • Busy projects keep their slot while the next cron tick advances.
  • Overlapping starts, duplicate renewals, and stale workers preserve ownership.
  • The sweep respects its limit, picks oldest schedules first, and catches up next time.
  • Dead scans are failed; long-running scans with fresh leases survive.
  • Insert and hand-off failures clean up correctly. Cross-organization adoption is rejected and terminal verdicts cannot be overwritten.
packages/geo-core/tests/scan-lifecycle.test.ts
Runs for real

Production scheduling, claim, hand-off and finalization functions. Drizzle executes SQL in PGlite using DDL generated from production tables, with indexes and foreign keys.

Replaced boundary

The workflow starter, external box cleanup, and logging transport. PGlite is embedded Postgres and serializes requests; it is not a multi-connection concurrency test.

Cron HTTP contract

8 new
  • Four missing or invalid authorization variants are rejected before any sweep.
  • An absent CRON_SECRET fails closed.
  • Authorized calls return the actual sweep counters.
  • Sweep failures propagate instead of returning success.
  • vercel.json registers the endpoint every ten minutes.
apps/dashboard/tests/geo-scan-cron.test.ts
Runs for real

The route’s GET handler, native Request/Response objects, authorization logic, and reading the deployment configuration.

Replaced boundary

The sweep and dashboard service layer. The handler is called directly; no Next.js HTTP server or Vercel cron delivery is involved.

Scan workflow orchestration

7 new
  • Invalid payloads and missing or skipped projects never run batches.
  • Tasks and sequences are split into the configured batch sizes.
  • Renewed tokens, check counts, mentions, and token usage move through the chain correctly.
  • A failed later batch finalizes with the accumulated results and latest token.
  • Only projects without successful checks retry, using fresh scan ownership.
  • A second empty attempt throws a fatal error instead of retrying forever.
apps/dashboard/tests/geo-scan-workflow.test.ts
Runs for real

The workflow’s branching, batching, token propagation, totals and retry decisions, executed as an ordinary function.

Replaced boundary

Step functions and sleep. This tests orchestration logic, not SDK compilation, durable waits, persisted replay, or restart recovery.

GitHub activity polling

7 new
  • Published releases and commits become content signals.
  • Repeated polls produce stable deduplication keys, scoped to the integration.
  • Drafts and prereleases are ignored.
  • Releases and commits obey the lookback window.
  • A deleted repository or missing credentials do not stop healthy repositories.
  • An empty integration list skips credential lookup.
packages/ai/tests/github-poll.test.ts
Runs for real

The production poller, Octokit, HTTP requests, and signal conversion. Emulate provides a local stateful GitHub API, seeded and changed through API requests.

Replaced boundary

Database repository discovery, credential lookup, and the Octokit factory’s base URL. No live GitHub account is queried.

Recurring content schedule timing

18 new
  • Six invalid dates are rejected, and a valid leap day is preserved.
  • Six delivery-time cases verify the correct scheduled day, including late arrival past midnight.
  • Four next-run cases cross month boundaries without resetting the interval.
  • A daylight-saving transition preserves the UTC schedule time.
packages/ai/src/utils/schedule-interval.test.ts
Runs for real

Production UTC date parsing, interval eligibility and next-run calculations with explicit timestamps.

Replaced boundary

Why two testing tools?

Emulate for APIs.
PGlite for database behavior.

Vercel Labs Emulate gives the GitHub tests a stateful local API. The scan tests need SQL constraints and conditional updates, so they use PGlite. Neither tool proves that Vercel delivers a cron request or durably resumes a workflow.

05 / The honest boundary

What green does not prove.

This is a foundation for regression protection. These remaining layers need their own tests.

Deployed cron & workflow runtime

No check yet for actual Vercel cron delivery, durable sleep, workflow replay, or recovery after a runtime restart.

Real Postgres connection races

PGlite runs actual SQL but serializes requests. Separate connections and PostgreSQL locking behavior still need a server-backed test.

Live models & billing

The suite does not validate model answer quality, provider availability, or actual usage charges against billing providers.

Database migration history

Tests generate tables from the current schema. They do not apply or validate the committed migration chain from an empty database.

Useful next additions: a server-backed Postgres concurrency test, a Workflow SDK runtime integration test, then a deployed smoke test that follows a scheduled scan from delivery to its persisted outcome.
