If you want to build a Grok Bot plugin, you are building a Cursor plugin. Literally. You package the integration in a repository and submit it through [Cursor's marketplace](https://cursor.com/marketplace/publish).

One plugin gets your product into both. If you already maintain a Cursor plugin, start there.

## What is Grok Bot? [#what-is-grok-bot]

[Grok Bot](https://x.ai/news/introducing-grok-bot) gives you agents that have their own computer and can work across apps. Give a bot a task, like researching a marketing campaign, and it works through it with you.

Plugins connect those agents to services. A user adds a plugin, authorizes their account and can ask the bot to work with that service in chat. Cursor documents that flow in its [Grok Bot plugin guide](https://cursor.com/help/grok-bot/connect-plugins).

## Why you should build one [#why-you-should-build-one]

A plugin puts your product where people are already working. They can connect it to their agent and try it on a real task. That's why I see it as a distribution opportunity, much like [building useful tools for engineers](/blog/engineers-are-great-for-marketing).

Start with something your users already ask for: creating a database branch or saving a content draft for review. Give them one reason to install it.

## Context.dev is a good example [#context-dev-is-a-good-example]

[Context.dev](https://context.dev/?ref=notra) is [listed in Cursor's marketplace](https://cursor.com/marketplace/context.dev) and its [plugin source is public](https://github.com/context-dot-dev/cursor-plugin).

The plugin gives agents tools for live web research, including search and scraping. Its README explains how users connect their Context.dev account through OAuth and gives them tasks to try after installation.

<figure data-width="100" data-align="center"><img className="block dark:hidden" src="/blog/grok-bot-gtm-result-light.png" alt="The Notra GTM Bot using Context.dev to research Notra's homepage and return positioning takeaways." /><img className="hidden dark:block" src="/blog/grok-bot-gtm-result-dark.png" alt="The Notra GTM Bot using Context.dev to research Notra's homepage and return positioning takeaways." /><figcaption>Context.dev turns a live page into useful research inside a Grok Bot conversation.</figcaption></figure>

I would start by reading these files:

- [`.cursor-plugin/plugin.json`](https://github.com/context-dot-dev/cursor-plugin/blob/main/.cursor-plugin/plugin.json) declares the plugin and points to its components.
- [`mcp.json`](https://github.com/context-dot-dev/cursor-plugin/blob/main/mcp.json) connects it to the hosted MCP server.
- [`skills/context-search/SKILL.md`](https://github.com/context-dot-dev/cursor-plugin/blob/main/skills/context-search/SKILL.md) explains when to search and when to scrape a known URL instead.

That's the part I would copy. If the user gives the agent a URL, the skill tells it to scrape that page instead of searching again. It teaches the agent how to use the product.

## What it takes [#what-it-takes]

A Cursor plugin needs a manifest at `.cursor-plugin/plugin.json` and skills that describe how to do a task. An optional MCP configuration connects the agent to your service.

Reuse your MCP server if you have one. If you only have an API, you'll need to build and host an MCP server for a remote connector like the example below.

For documented workflows that don't need account access, a plugin containing only skills may be enough.

## Create the plugin [#create-the-plugin]

If you are asking an agent to build this, give it the official docs before it starts. The [Cursor plugins overview](https://cursor.com/docs/plugins) covers installation and local testing. The [plugin reference](https://cursor.com/docs/reference/plugins) covers the manifest and submission requirements. Add the [MCP docs](https://cursor.com/docs/mcp) if your plugin connects to a service.

You can start with this prompt and add your product's API documentation:

```text
Build a Cursor plugin for our product that we can submit for use in Grok Bot.
Read these docs first:
https://cursor.com/docs/plugins
https://cursor.com/docs/reference/plugins
https://cursor.com/docs/mcp

Use the Cursor plugin format with .cursor-plugin/plugin.json.
Read https://github.com/context-dot-dev/cursor-plugin as a packaging example.
Start with one useful workflow based on our product docs.
Reuse our MCP server if we have one. If we don't, explain what needs to be
implemented before the connector will work. Don't invent an endpoint or tools.
Include a skill and a README with setup instructions and a test task.
Prepare the repository for review. Submission goes through
https://cursor.com/marketplace/publish.
```

[Cursor's template](https://github.com/cursor/plugin-template) is a starting point. It includes multiple plugins, so simplify it if you only need one. A small repository could look like this:

```text
acme-plugin/
├── .cursor-plugin/
│   └── plugin.json
├── skills/
│   └── draft-release-note/
│       └── SKILL.md
├── mcp.json
└── README.md
```

Acme is a fictional content product for this walkthrough. Put this in `.cursor-plugin/plugin.json`:

```json
{
  "name": "acme-content",
  "version": "0.1.0",
  "description": "Prepare release notes and save drafts in Acme.",
  "author": {
    "name": "Acme"
  },
  "skills": "./skills/",
  "mcpServers": "./mcp.json"
}
```

Use your own name and description. Cursor also supports the portable Agent Plugins format with a root `plugin.json`; this walkthrough uses the Cursor format. The [plugin reference](https://cursor.com/docs/reference/plugins) documents both.

### Write the skill [#write-the-skill]

The skill should explain when to use it and what a completed task looks like. Here's an example for `skills/draft-release-note/SKILL.md`:

```markdown
---
name: draft-release-note
description: Prepare a release note from supplied product changes and save it as an Acme draft. Use when the user asks to draft a release announcement.
---

# Draft a release note

Read the changes the user supplied. Ask for source material if it is missing.

Explain what changed and who it affects. Do not invent features or results.

Show the draft to the user. When asked to save it, use the Acme connector's
draft creation tool. Ask which workspace to use if the destination is unclear.

Return the saved draft's link. Saving a draft does not authorize publication.
If the connector is unavailable, return the text and explain that it was not saved.
```

Replace the generic tool reference with your server's actual tool name.

### Connect your tools [#connect-your-tools]

For a Cursor plugin using a remote MCP server, `mcp.json` can look like this:

```json
{
  "mcpServers": {
    "acme": {
      "url": "https://mcp.example.com/mcp"
    }
  }
}
```

That is a placeholder URL. Replace it with your working MCP endpoint. If you are making a skill-only plugin, remove this file and the `mcpServers` field from the manifest.

For a service with private accounts, the server also needs an authentication flow supported by the client. Follow [Cursor's MCP documentation](https://cursor.com/docs/mcp) for the connection setup. Keep credentials out of the repository and enforce account permissions on the server.

Write a README that explains setup and includes a first task to try. Describe what the tools can change so users know what they are connecting.

## Test the whole task [#test-the-whole-task]

You can [test a plugin locally in Cursor](https://cursor.com/docs/plugins#test-plugins-locally) by putting the plugin folder under `~/.cursor/plugins/local/`, then reloading Cursor. Open Customize and check that the expected components appear. Team policy can block local imports and an installed marketplace plugin with the same name takes precedence over the local copy.

Then try the task in a fresh conversation. For the example above, supply a short list of changes and ask for a release note. Check whether the bot sticks to those changes. Connect a test account, save the draft and open the returned link to verify the result.

Try it with the connector disconnected too. It should explain what failed instead of claiming the draft was saved. Also check what happens when the user has access to more than one workspace.

## Submit through Cursor's marketplace [#submit-through-cursors-marketplace]

Push the plugin to a public Git repository and submit its link at [cursor.com/marketplace/publish](https://cursor.com/marketplace/publish). The Cursor team reviews plugins before listing them.

Before submitting, check that the manifest paths resolve and the README explains any configuration. If you include a logo, commit it to the repository and reference it with a relative path. Cursor's [submission checklist](https://cursor.com/docs/reference/plugins#submission-checklist) covers the requirements.

After approval, install the plugin in Grok Bot and run your README's example with a test account. Record that flow for your announcement.
